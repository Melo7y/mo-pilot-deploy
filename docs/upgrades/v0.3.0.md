# v0.3.0-rc.2 测试环境交付与升级

本次交付为测试候选版 `v0.3.0-rc.2`，由操作者完成镜像构建和测试服务器升级。包含需求三个视图与团队筛选、预估总工时与到期提示、需求参与人员、本人评论编辑与软删除。

支持以下两种起点，均使用本文整套升级流程：

- **v0.2.0 / 迁移 00011**：前后端配套更新，数据库迁移 00011 → 00013。
- **v0.3.0-rc.1 / 迁移 00013**：本次仅调整前端评论交互；后端源码未变化，无新增迁移。统一执行 `migrate up` 时应保持 00013。

若是全新服务器，先按[部署 README](../../README.md)准备首次安装，不执行本文的存量升级流程。

## rc.2 相对 rc.1 的变化

- 编辑评论时输入框替换正文，移除重复内容及双层背景；输入区自适应高度，字数、取消及蓝色保存位于底栏。
- 桌面默认隐藏“编辑 / 删除”，鼠标移入评论框或键盘聚焦时显示；触屏保留入口，显隐不引起布局跳动。
- 保留原有作者权限、附件、保存失败草稿及并发冲突对照。需求和任务详情共用此交互。
- 使用新的 `v0.3.0-rc.2` 镜像及升级包，不覆盖 rc.1 产物。前端候选提交为 `5a89bad7aa9712fb36e3fbd9ea30ca5c01010610`，后端仍为 `68bb5e1888b21bb4a9d3fcbcbf8e4634341fcbb7`。

## 1. 准备升级包

### 方式一：在本机从已提交代码打包

三个仓库的 `feat/requirement-collaboration` 候选分支均已推送成功。可使用本节的本机打包方式，也可使用下节的测试服务器直接打包方式。下面的命令使用本地固定提交。

在这台开发 Mac 上启动 Docker Desktop，再执行以下完整代码块。示例目标服务器为 x86_64；如服务器是 aarch64/ARM64，将 `PLATFORM` 改为 `linux/arm64`。可在服务器执行 `uname -m` 确认，勿按 Mac 自身架构选择。

```bash
bash <<'PACKAGE'
set -euo pipefail
cd /Users/melo/code/mo-pilot/mo-pilot-deploy
TAG=v0.3.0-rc.2
PLATFORM=linux/amd64
WEB_SHA=5a89bad7aa9712fb36e3fbd9ea30ca5c01010610
API_SHA=68bb5e1888b21bb4a9d3fcbcbf8e4634341fcbb7
DEPLOY_SHA="$(git rev-parse --verify 'feat/requirement-collaboration^{commit}')"
bash scripts/package.sh "$TAG" "$PLATFORM" "$WEB_SHA" "$API_SHA" "$DEPLOY_SHA" 00013
PACKAGE
```

脚本只归档提交内容，不打包工作区修改或 `.env`。构建基础镜像和安装依赖仍需网络；Git 的 SSH 代理只影响 Git，Docker 构建沿用 Docker 自身网络配置及已导出的 `HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY`。不要修改现有代理配置来照抄示例。

成功时输出 `Package ready`，产物目录为：

```text
/Users/melo/code/mo-pilot/.scratch/packages/v0.3.0-rc.2/
├── mopilot-images-v0.3.0-rc.2.tar.gz
├── mopilot-deploy-v0.3.0-rc.2.tar.gz
├── source.txt
└── SHA256SUMS
```

核对 `source.txt`：版本为 `v0.3.0-rc.2`，平台匹配服务器，前后端 SHA 与上方一致，`required_migration=00013`。保留四个文件，同名包与不同来源的同名镜像不会被覆盖；后续修复使用 `v0.3.0-rc.3` 等新编号。

将整个 `v0.3.0-rc.2` 目录上传到测试服务器，例如现有部署目录同级的 `.scratch/packages/`。服务器最终应能读到 `../.scratch/packages/v0.3.0-rc.2/source.txt` 等四个文件；也可用其他目录，下一节填写其实际路径。现有环境默认只打包前后端，沿用服务器已有的 PostgreSQL 镜像。

### 方式二：直接在测试服务器打包

三个远程仓库已具备候选分支，无需再次从开发机推送。在测试服务器**现有部署目录**执行：

```bash
git fetch origin refs/heads/feat/requirement-collaboration &&
git show FETCH_HEAD:scripts/package.sh > /tmp/mopilot-package-v03.sh &&
MOPILOT_SOURCE_REF=feat/requirement-collaboration bash /tmp/mopilot-package-v03.sh v0.3.0-rc.2
```

要求同级存在 `frontend`、`backend` 两个 Git 仓库并配置 `origin`，以及 Docker Buildx。脚本从三个远程同名分支取得提交，自动检测本机 Docker 平台和最新迁移；不切换现有部署工作区。源分支不存在或 fetch 失败即中止，不会退回 main 打包。提交以实际 `source.txt` 为准，仍须核对为本次候选代码。

**不要直接使用默认 main 的单参数打包方式来获取本次未合并的功能。** 两种打包方式任选其一，无需重复。

## 2. 备份并升级

在测试服务器进入**现有部署目录**，打开[统一升级流程 B 的第 2 步](README.md#2-备份更新检查)，执行其中完整代码块，并将开头三个值替换为：

```bash
TAG=v0.3.0-rc.2
PACKAGE=../.scratch/packages/v0.3.0-rc.2
EXPECTED_MIGRATION=00013
```

如果上传到其他位置，将 `PACKAGE` 改为该目录的绝对路径。不要只执行这三行，它们是统一升级代码块的参数。

沿用现有 `.env`、Compose 项目名、域名、端口及持久化目录。若原环境启用了钉钉，把统一流程中的 `dc()` 改为下方形式；若原启动还使用 `-p`，继续保留原项目名：

```bash
dc() { docker compose --env-file .env -f compose.yaml -f compose.dingtalk.yaml "$@" </dev/null; }
```

统一流程会先校验四文件和版本、加载镜像，再备份配置，停止 web/api/backup，备份数据库和附件并校验，随后更新部署配置、迁移并启动。`.env` 不会被升级包覆盖，统一镜像标签更新为 `v0.3.0-rc.2`，前端独立标签清空。备份和迁移期间会有停机。

迁移 12 增加参与人员，13 增加评论版本、编辑/删除元数据和维护历史。已有参与人员默认为空；历史评论版本默认为 1，正文、作者和发布时间保留，无需补录。

## 3. 浏览器验收

先确认 API、Web、数据库为 `healthy`，backup 正在运行，迁移状态达到 00013，Nginx 配置检查通过。打开原测试地址并强制刷新，使用原账号登录。验收建议使用测试需求及本人测试评论：

- **列表**：普通需求和待安排列表均有“全部、我创建的、我负责的”视图；组合负责团队筛选，切页并从详情返回，检查筛选与总数保留。普通账号的数据权限保持原有范围。
- **工时与到期**：检查有估算、缺失估算及包含无权查看任务的需求；分别显示汇总、未完整/未估算、权限受限。到期提示按上海日期计算。
- **参与人员**：需求负责人、PM、项目助理、管理员可保存多行文本；普通无权限账号无编辑入口。双窗口同时修改时提示冲突，能对照最新内容且草稿保留。
- **评论（rc.2 重点）**：桌面移入本人评论框显示编辑/删除，移出隐藏；Tab 聚焦也显示，触屏入口常显。他人评论无维护入口。编辑时不重复展示正文；保存和取消均正常，附件保留；删除需确认，删除后保留占位且原附件链接不能再下载；双窗口冲突保留草稿与当前正文对照。需求及任务详情都要检查。
- **回归**：检查原需求、任务、甘特图、历史附件下载。启用钉钉时，再检查绑定及约定的通知场景。手机和钉钉客户端体验需要补充验收。

## 4. 失败处理与回退

打包失败不会停服务，检查错误后重试；升级在停机后失败时保持维护状态，保留输出及备份位置，先修复再继续。不要执行 `seed`、`bootstrap-admin` 或 `down -v`。

一旦产生评论编辑或删除记录，**不能仅替换回 v0.2.0 应用镜像**：旧版不识别删除标记，会重新展示已删除正文和附件。迁移 13 的 Down 在有维护历史时拒绝执行；迁移 12 在参与人员非空时拒绝移除字段。迁移保护不能阻止直接启动旧应用。

rc.2 与 rc.1 后端及数据库契约相同；若只回退本次前端交互，可按[统一流程 A](README.md#a-仅前端更新)的回退说明，将前端独立标签设为实际保留的 rc.1 前端镜像并仅重启 web，无需数据库降级。API 保持当前版本。

需要回到 v0.2.0 时，优先前滚修复；必须回退则停写，按[数据恢复流程](../../README.md#10-恢复)恢复**首次升级到 v0.3 之前、仍处于迁移 00011 的 v0.2.0 数据库备份**、对应附件及旧配置/镜像。rc.1 升 rc.2 前的备份已经是迁移 00013，不能用于回退到 v0.2.0。备份后的新增或修改数据将丢失。不要清空删除标记或维护历史来绕过保护。
